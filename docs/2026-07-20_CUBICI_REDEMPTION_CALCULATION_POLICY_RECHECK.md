# Cubici 상환 계산 로직 및 정책 재확인 항목

## 작업 결과

- 개발 완료 전후 반드시 재확인해야 할 상환/지급 계산 로직과 운영 정책을 정리한다.
- 현재 개발 중 임의 보정하지 않을 항목과 테스트 운영 단계에서 전체 DB로 검증할 항목을 구분한다.

## 재확인 대상

1. 상환 취소 재계산
   - 과거 상환을 취소할 때 해당 시점으로 되돌리지 않는다.
   - 최신 누적 지급/상환 상태에서 취소 금액을 역반영한다.
   - 원거래 row는 삭제하지 않고 취소 operation history를 추가한다.

2. 지급 취소 재계산
   - 과거 지급을 취소할 때 후속 상환/지급이 이미 존재할 수 있다.
   - 최신 누적 상태 기준으로 지급 금액을 차감한다.
   - 취소 후 누적 지급액, 누적 상환액, 미상환잔액이 음수가 되면 거부한다.

3. 미상환잔액 산식
   - 기본 산식은 `outstanding_balance = cumulative_provision_amount - cumulative_repayment_amount`로 본다.
   - legacy DB의 기존 row 중 이 산식과 불일치하는 케이스는 개발 중 임의 보정하지 않는다.
   - 개발 완료 후 테스트 운영 단계에서 전체 DB 기준으로 점검한다.

4. 중복 취소 방지
   - 동일 operation history는 한 번만 취소 가능해야 한다.
   - 취소 operation 자체는 다시 취소하지 않는다.

5. 원장 보존 정책
   - 지급, 상환, 입금, 판매 원천 row는 삭제하지 않는다.
   - 정정/취소는 별도 operation history로 감사 추적 가능해야 한다.

6. 금액 검증
   - 지급액은 결제금액을 초과하지 않아야 한다.
   - 상환액은 현재 미상환잔액을 초과하지 않아야 한다.
   - 입금액과 상환액의 관계는 운영 정책 확정 후 재검토한다.

7. 정산/상환 연결
   - 정산 완료, 지급, 상환, 입금 간 상태 전이가 실제 업무 흐름과 맞는지 재확인한다.
   - batch 처리와 관리자 수기 처리의 우선순위를 분리한다.

## 검증 시점

- API/관리자 핵심 기능 개발 완료 후
- 테스트 운영 DB에서 반복 입력/취소/정정 시나리오 수행 시
- 운영 전 전체 DB reconciliation 수행 시
